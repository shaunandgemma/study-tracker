4. KEY RECOVERY CORRECTION

Stage 12 now recovers an existing hosted Candidate Approval Key from the protected candidate record after a reload.

The Author no longer depends on the temporary in-page candidate state to retrieve the key.

The recovered key is displayed only for the signed-in Author who can read their own protected candidate record.

5. LOCAL-PACKAGE WORDING CORRECTION

Local packages now display:

1. Local Package ID.
2. Local package only - approval unavailable.
3. Prepare New Local Package.

They no longer display wording that can be mistaken for a hosted approval candidate.

6. TWO HASH BOUNDARIES

The app and protected database use two valid SHA-256 representations for different purposes:

1. The app canonical snapshot hash creates and verifies the Candidate Approval Key suffix.
2. The protected database JSONB hash protects the stored immutable candidate snapshot.

The verifier now checks each hash against its correct boundary instead of comparing the two different representations directly.

7. RECOVERED-CANDIDATE CHECKS

The recovered candidate must pass:

1. Candidate key suffix matches the app canonical snapshot hash.
2. Protected server snapshot hash is a valid SHA-256 value.
3. Candidate snapshot matches the current Shared Draft release snapshot.
4. Candidate source revision matches the current saved revision.
5. Candidate creator matches the signed-in Author.
6. Candidate draft-content hash matches the protected saved Shared Draft hash.
7. Candidate status is awaiting trusted approval.
8. Candidate approval decision is pending.

8. DUPLICATE PROTECTION

After the existing candidate is found:

1. The readiness panel says an immutable candidate already exists.
2. The candidate-generation button is disabled.
3. The existing key is recovered and verified.
4. No second insert is attempted.
